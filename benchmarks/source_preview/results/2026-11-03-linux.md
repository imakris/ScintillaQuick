# Source-preview scrollbar performance — 2026-11-03

## Result and scope

The optimized preview produces the same measured pixels while substantially
reducing the time to rebuild its source image. For the real 9,188-line
`Editor.cxx` input, median initial action-to-rendered-preview time fell from
502.9 ms to 261.0 ms; a same-line edit fell from 463.0 ms to 271.5 ms. Unique
10,000-line source improved from 933.5 ms to 518.7 ms initially. Identical
repeated lines benefit much more, while large unique documents still require a
linear full-document pass. The tables below preserve the distributions and
separate those cases. [Accepted measurement evidence](2026-11-03-linux-evidence.json)

This work improves asynchronous **source-image refresh**. It does not establish
a scrolling-FPS improvement or whole-application latency reduction. Native
Windows rendering correctness was exercised by CI, but the performance
measurements in this report use Linux software rendering.

## What caused the cost

The first diagnostic exercised the actual `Raster_worker::begin()` and
`consume()` implementation directly, with 20,000 styled lines and a
92 × 600-pixel output. It excluded GUI capture, queued handoffs, scene-graph
work and physical display. Timers around the individual worker stages showed
that layout and glyph drawing dominated; reducing the final row into the small
image was a much smaller part of the work. These were diagnostic single
samples, not the repeated production-path results reported later.

For unique ASCII lines, the instrumented baseline spent approximately 697 ms
in layout and 891 ms in drawing, out of 1,934 ms total. The 179 ms decoding
measurement included approximately 150 ms creating text formats; those nested
times must not be added together. Downscaling took approximately 118 ms and
row compositing 11 ms. [Diagnostic stage measurements](2026-11-03-linux-evidence.json)

### Preserve the prepared layout through drawing

The old code constructed a `QTextLayout`, completed its layout and immediately
drew it with layout caching disabled. Qt documents that ordinary
`endLayout()` discards much of the prepared layout information, and recommends
enabling the cache when drawing immediately afterward.
[Qt `QTextLayout::setCacheEnabled()` documentation](https://doc.qt.io/qt-6/qtextlayout.html#setCacheEnabled)

Enabling this cache alone reduced the diagnostic unique-ASCII drawing stage
from approximately 891 ms to 367 ms. In the separate uninstrumented worker
sample, the same one-line change reduced total work from 1,841 ms to 1,350 ms.
The corresponding diagnostic reductions were 22.8% for repeated ASCII, 35.5%
for Unicode and 36.2% for long prefixes. Every diagnostic image comparison
matched. These single-sample numbers identify the cause; they are not a claim
about the complete optimized application. [Diagnostic evidence](2026-11-03-linux-evidence.json)

The production change also reuses the layout object and its common text
options within one existing bounded chunk. Each source line replaces the
text and formats before layout. The layout is destroyed before acknowledging
the chunk, so this does not retain layouts for the entire document.

### Reuse style formats and avoid decoding temporaries

The worker lazily prepares each used `QTextCharFormat` once per chunk and
reuses it for that chunk's style ranges. UTF-8 decoding reserves the known
upper bound for the UTF-16 output, fills its byte buffer through one writable
pointer, and appends UTF-8 views directly instead of allocating a temporary
`QString` for every fragment. The leading UTF-8 byte still selects the
character's style. Tests preserve clipped tails, malformed input and the
existing embedded-BOM behavior.
[Production change](https://github.com/imakris/ScintillaQuick/commit/9b477b7683ba9d50abebec5e74e5f6e8ae3c183b)

### Reuse identical compressed rows within a generation

When several document lines fit in one output pixel row, an exact repeated
styled prefix can reuse its already rasterized transparent row. The cache key
contains both the UTF-8 bytes and their style bytes. Each cache hit still
composites that row at the current logical line's position, in document order;
repetition is not skipped or replaced by a sampled line.

The cache is scoped to one worker's immutable capture generation. Its charge
is limited to 256 KiB, and a minimum charge of 512 bytes limits it to at most
512 entries. Each entry's charge includes image bytes, retained styled-input
capacity, `sizeof(QImage)` and a 128-byte bookkeeping allowance. This is an
explicit cache accounting limit, not a claim that total process memory or
Qt's own font/glyph caches are capped at 256 KiB. It is per worker, not a
global budget across all editors.

New configurations, completed generations and cancellation clear the cache.
Failed row allocations are not cached. The ordinary uncompressed-line path
keeps its existing drawing behavior. The existing worker thread, capture
slice/chunk limits, clipping horizon, generation checks, line mapping and
source-over accumulation remain in place.
[Cache implementation](https://github.com/imakris/ScintillaQuick/commit/f713fc8f91d688180b3aa85593bbb16375be8689)

## Measurement method

The accepted measurements use Ubuntu 24.04.3 x86-64, GCC 13.3, a Release build
and Qt 6.12.0 from Linux SDK `2026.10.23.1`. The host reports an AMD EPYC 9V74
processor; this is a container environment, not a dedicated bare-metal
performance laboratory. The bundled Cascadia Code font is used at 11 points
and 96 font DPI. Preview size is 96 × 720 logical pixels, with device pixel
ratio 1 except for the explicitly marked DPR 2 case.

Each case uses three pairs in baseline/optimized, optimized/baseline,
baseline/optimized order. Each side runs in a fresh process with
`--iterations 1`; the later scenarios in that process can use its already
warmed font caches. Builds and other intentional benchmarks were not run
concurrently. Reported improvements compare medians; three pairs give useful
ranges but do not establish a statistical confidence interval.

The benchmark records these separate boundaries:

| Field | Included work |
| --- | --- |
| `setup_ms` | Native document loading and deterministic style assignment, reported separately from the preview timings. |
| `trigger_ms` | Synchronous preview attachment, refresh request or native edit. |
| `publication_ms` | Trigger through observation of a new nonzero GUI publication serial, including normal debounce, native capture, worker rasterization and queued handoffs. |
| `software_frame_ms` | One actual offscreen Qt Quick software preview frame after publication. |
| `rendered_ms` | Trigger through that completed frame; this is the main table metric below. |
| `process_cpu_ms_to_publication` | Linux process CPU time through publication, including GUI and raster-worker work. |
| `gui_1ms_timer_gaps` | Observed gaps of a precise 1 ms GUI timer, including scheduler/timer resolution and benchmark overhead. This is not isolated capture time or keyboard latency. |

Corpus generation, file reading, native text loading and style preparation
precede preview timing. Image hashes and pixel comparisons occur after the
frame clock stops. Only the preview is drawn: host-editor painting, native
input delivery, display presentation, and the rest of Logonomic are outside
the timed boundary. Publication polling adds approximately timer-resolution
granularity; it does not explain the large observed reductions.

The real-file case uses `third_party/scintilla/src/Editor.cxx` unchanged:
286,908 bytes and 9,188 logical lines. All inputs receive the same deterministic
small token classifier before timing; these are styled-document measurements,
not measurements of Lexilla. Generated unique identifiers vary inside the
captured prefix. The repeated, sparse, Unicode and long-line cases are
identified separately rather than pooled into one headline result.
[Benchmark contract](../README.md) · [Accepted inputs and observations](2026-11-03-linux-evidence.json)

## Scrolling and correctness

Scrolling reuses the completed source image and moves the viewport overlay.
The benchmark verifies both rendered handle movement and an unchanged source
publication serial over 120 scroll steps and a subsequent debounce interval.
All accepted scrolling cases passed.

These small software-frame timings moved in both directions: medians of the
per-run scroll-step medians were 0.132 → 0.148 ms for `Editor.cxx`,
0.136 → 0.132 ms for unique 10,000-line source and 0.288 → 0.298 ms at DPR 2.
They do not demonstrate a scrolling speedup, and no FPS improvement is claimed.
The material measured change is the wait for a newly completed source image.
[Scroll checks and timings](2026-11-03-linux-evidence.json)

The [maintained raster test](../../../tests/source_preview_raster/main.cpp)
checks per-line contributions against independent fresh single-line workers
composited in document order. It covers repeated rows, differing styles,
Unicode, clipping, malformed sequences, embedded BOMs, chunk boundaries,
configuration changes, cancellation and preservation of retained images.
Existing source-preview scene-graph tests additionally cover overlays,
navigation, mode changes, wheel forwarding, geometry changes and retained
rasters during edits. All accepted baseline/optimized benchmark images matched
exactly for their corresponding input, geometry and scenario.

Local Linux Release validation passed all five selected gates:
`scintillaquick_frame_validation_test`,
`scintillaquick_source_preview_raster_test`,
`scintillaquick_preview_software_test`, and the software renderer-conformance
tests at DPR 1 and 1.25. Local RHI execution was unavailable in this container;
it is not represented as a passing local GPU test.

The accepted main set, `paired-main`, contains seven cases and 42 complete
process runs. The accepted DPR 2 set, `paired-dpr2`, contains three new pairs
and six complete runs. The million-line set, `paired-million`, adds three pairs and six complete runs.
All three accepted sets passed metadata matching and image-hash comparison
without discrepancies: 54 fresh process runs, 75 paired rendered-image checks
and nine paired scrolling checks. Their compact observations, executable

The first 48-run collector retained one unexpectedly empty DPR 2 JSON file
although the subprocess had reported success. The original collection was
preserved under `paired-final`; its entire DPR 2 case was excluded from the

missing/excluded output is used to calculate the tables above.

## Reproduction

Use the same compiler, Qt runtime, bundled font, geometry and software backend
for both revisions. Build fresh directories; do not compare a debug binary
with a Release binary. The benchmark is opt-in and its timing results are not
CTest pass/fail thresholds.

```sh
git worktree add --detach ../preview-before 2cb46df0b859f48a302a2c1f3d1cd73319689666
git worktree add --detach ../preview-after f713fc8f91d688180b3aa85593bbb16375be8689

# Activate the Linux SDK before configuring or running either side.
source /path/to/logonomic-linux-development-sdk-2026.10.23.1/activate.sh

for variant in before after; do
    queued-build --slots 1 -- cmake -S "../preview-$variant" \
        -B "../preview-$variant/build-preview" -G Ninja \
        -DCMAKE_BUILD_TYPE=Release -DCMAKE_CXX_COMPILER=g++-13 \
        -DBUILD_SHARED_LIBS=OFF -DSCINTILLAQUICK_BUILD_BENCHMARKS=ON
    queued-build --slots 4 -- cmake --build "../preview-$variant/build-preview" \
        --target scintillaquick_source_preview_benchmark --parallel 4
done
```

Run from each source checkout so its bundled fonts can be found. The following
arguments reproduce the input/scenario selections; use `--iterations 1` and
repeat each complete command in before/after, after/before, before/after order,
saving a distinct JSON output for every process. Avoid concurrent builds or
other intentional benchmarks while collecting paired measurements.

| Case | Additional arguments |
| --- | --- |
| Real source | `--input-file third_party/scintilla/src/Editor.cxx --scenario all` |
| Unique 10k | `--lines 10000 --corpus unique --scenario all` |
| Unique 100k | `--lines 100000 --corpus unique --scenario initial,edit` |
| Repeated 100k | `--lines 100000 --corpus repeated --scenario initial,edit` |
| Unicode 10k | `--lines 10000 --corpus unicode --scenario initial,refresh,edit` |
| Long 1k | `--lines 1000 --corpus long --scenario initial,refresh,edit` |
| Sparse 100k | `--lines 100000 --corpus sparse --scenario initial,edit` |
| DPR 2 | `QT_SCALE_FACTOR=2`, with `--lines 1000 --corpus unique --scenario all` |
| Unique 1M | `--lines 1000000 --corpus unique --scenario initial --timeout-ms 300000` |

For example, one baseline real-file process is:

```sh
cd ../preview-before
QT_QPA_PLATFORM=offscreen QT_FONT_DPI=96 QT_SCALE_FACTOR=1 \
    ./build-preview/scintillaquick_source_preview_benchmark \
    --iterations 1 --input-file third_party/scintilla/src/Editor.cxx \
    --scenario all --output /absolute/path/to/editor-pair-01-before.json
```

Compare input hashes, line/byte counts, Qt/font/backend/DPR metadata and image
hashes before comparing times. Keep raw process observations and report their
range as well as their median. Full parameter and measurement descriptions
are in the [benchmark README](../README.md).

## Remaining limit

The implementation still captures every relevant logical source line and
still shapes each unique styled prefix. A full refresh is therefore O(N) in
document lines, even though the preview image has a fixed pixel budget. At
100,000 unique lines the measured optimized initial image still takes about
6.5 seconds, and a same-line edit still causes a roughly 6.0-second rebuild.
At one million unique lines, the initial rendered preview improved from
91.37 seconds [89.53–91.86] to 51.52 seconds [50.99–52.27], a 43.6%
reduction. The improvements are substantial but do not make large unique
documents instantaneous. [Measured large-file results](2026-11-03-linux-evidence.json)

Incremental invalidation or a different large-document rendering strategy
would be further work. This patch keeps the existing visual and navigation
contract, including every line's contribution, exact style-sensitive reuse,
bounded work/storage and stale-generation rejection. It uses the existing
worker thread and preserves the image quality and every source line's contribution.
The remaining large-file scaling cost is explicit in the measurements above.
